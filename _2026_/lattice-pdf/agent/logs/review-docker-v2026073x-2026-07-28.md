### 🔴🔴 B0. `compute_ope_gpu.py` — v20260731 缺少 v20260730 的双场强（dual field strength）OPE 算法

**这是两个版本之间最严重的不一致。** 两个版本的 OPE 算符构造使用了**完全不同的数学公式**：

**v20260730 实现** (donghx 算法):
- `build_tensor4()` (第43行): 构建 $T_4 = 0.5 \cdot \varepsilon_{\mu\nu\rho\sigma}$ Levi-Civita 张量
- `compute_dual_field_strength_munu()` (第140行): 计算对偶场强 $\tilde{F}_{\mu\nu} = 0.5 \cdot \varepsilon_{\mu\nu\rho\sigma} \cdot F_{\rho\sigma}$
- `compute_ope_donghx_gpu()` (第290行): OPE 公式 $O(z) = \sum_x \operatorname{Tr}[F(x+z) \cdot W^\dagger \cdot \tilde{F}(x) \cdot W]$
- 约 500 行代码

**v20260731 实现** (简化算法):
- `compute_ope_per_component_gpu()` (第243行): 使用累积正向传输子 $C(x) = \prod_{s=0}^{x-1} U(s, z_{\text{dir}})$
- OPE 公式 $O(z) = \sum_x \operatorname{Tr}[F(x+z) \cdot C(x+z)^\dagger \cdot C(x) \cdot F(x) \cdot C(x)^\dagger \cdot C(x+z)]$
- 约 120 行代码
- **没有** `build_tensor4()`、`compute_dual_field_strength_munu()` 或 `compute_ope_donghx_gpu()`

**两个公式不是数学等价的：**
1. v20260730 使用 $\tilde{F}$ (dual) → 混合了电场和磁场分量
2. v20260731 使用 $F$ (direct) → 仅使用原始场强分量
3. v20260730 使用基于 `roll` 的 Wilson 线传输；v20260731 使用累积乘积传输子

**观测到的数值差异证实了算法差异：**

| 版本 | $\vert O\vert$ 典型范围 | 虚部 |
|------|--------------------------|------|
| v20260730 (dual F̃) | $\sim 50$ | $\sim 10^{-15}$ |
| v20260731 (direct F) | $\sim 240$ | $\sim 10^{-15}$ |

比值 $R(z) = C_3^{\text{disc}} / C_2$ **可能仍然正确**，因为 $C_3$ 和 OPE 内部一致——但需要与参考结果（donghx/huangcl 预计算 OPE）交叉验证后才能确认。

**建议**: 将 v20260730 的 `build_tensor4()`、`compute_dual_field_strength_munu()` 和 `compute_ope_donghx_gpu()` 完整移植到 v20260731，并添加测试确认与 v20260730 数值一致。

**影响分析**: 虽然有效质量正确匹配（$m_{\text{eff}}$ 差异 $< 10^{-4}$ GeV），但有效质量仅验证了 2pt 蒸馏部分（Step 1），而非 OPE 部分（Step 2）。$R(z)$ 比值可能因 OPE 算法差异而产生系统性偏差，影响后续的匹配核和 PDF 提取。

### 🔴 B1. `compute_2pt_gpu.py` — Perambulator 读取逻辑版本间不一致（数据正确性风险）

**v20260730 实现** (`_read_perambulator_file`):
```python
# 每个 (tsrc, dsrc) 文件: (Nt, Nev_snk, Nspin=4, Nev_src, 2) LE f8
raw = raw.reshape(Nt, Nev, Nspin, Nev, 2)  # → (Nt, Nev, 4, Nev)
# Stack 4 dsrc → transpose: (Nt, 4, 4, Nev, Nev)
peram = np.stack(parts, axis=0).transpose(1, 3, 0, 4, 2)
```

**v20260731 实现** (`read_perambulator_single_t`):
```python
# 每个 (tsrc, dsrc) 文件: 4个文件拼接 → reshape (4, Nt, Nev, 4, Nev, 2) → transpose (Nt, 4, 4, Nev, Nev)
peram = raw.reshape(4, Nt, Nev_full, 4, Nev_full, 2).transpose(1, 3, 0, 4, 2, 5)
```

**风险分析**: 两个版本的 perambulator 重塑/转置逻辑完全不同。v20260730 使用 `np.stack` + 显式 transpose，v20260731 使用 `np.concatenate` + 单次 reshape。如果两种方式的最终形状 (`Nt, 4, 4, Nev, Nev`) 实际排列不同，会得到不同的 Wick 收缩结果。但从运行结果来看，两个版本的有效质量一致（diff < 1e-4 GeV），说明当前数据下两者等价。

**建议**: 添加跨版本的 perambulator 读取单元测试，直接对比两个版本对同一输入文件的输出。

### 🔴 B2. `config.json` — 两版本路径模式语义不同（移植性陷阱）

### 🔴 B3. `compute_2pt_gpu.py` — v20260730 的 `_read_eigenvector_slice` 使用 `reshape(Nev, Nv, Nc, 2)` 而非 `[::2]+1j*[1::2]` 交错读取

**v20260730**:
```python
raw = raw.reshape(Nev, Nv, Nc, 2)  # (Nev, Nv, Nc, 2)
return raw[..., 0] + 1j * raw[..., 1]
```

**v20260731**:
```python
comp = raw[::2] + 1j * raw[1::2]  # interleaved: re,im,re,im,...
comp = comp.reshape(Nev_full, Nx**3, Nc)
```

**风险**: 两种编码方式等价 **仅当** 二进制文件中的复数存储为 $(re_0, im_0, re_1, im_1, ...)$。如果数据实际存储为 $(re_0, re_1, ..., re_n, im_0, im_1, ..., im_n)$（分离式），则 v20260731 的交错读法会得到错误结果。由于两个版本都产生了正确的有效质量，当前数据是交错格式。但如果数据源格式改变，v20260731 会在没有警告的情况下产生静默错误。

**建议**: 添加明确的格式检测：读取前几个值，检查其模是否在合理范围内（$|z| \in [10^{-6}, 10^2]$），拒绝明显错误的排列。

## 六、性能与优化建议

### 🔵 P1. VVV 逐 $x$ 方向循环可批量化

两个版本的 VVV 计算都使用逐 $x_i$ 循环：
```python
for xi in range(Nx):
    s, e = xi * L, (xi + 1) * L
    ...
```

24 次独立的 einsum 调用增加了 kernel launch 开销。可以合并所有 $x_i$：
```python
# 替代方案: 将 x 维度合并到 batch 中
T = cp.einsum("x,iax,ibx->iabx", phase_gpu_2d, eigvecs_t_gpu[..., 0], eigvecs_t_gpu[..., 1])
```

这会将 24 次 kernel launch 减少为 1 次。

---

### 🔵 P2. Wick 收缩内存分配模式

双精度 Wick 收缩慢约 12-15×（远超预期的 2×）。问题可能在于每个 `(t_snk, t_src)` 对都分配临时张量并立即释放，导致 GPU 内存碎片化。

**建议**: 预分配最大中间张量并在循环中复用：
```python
T_buf = cp.zeros((max_Nev, max_Nev, max_Nev, 4), dtype=compute_dt)
```

---

### 🔵 P3. Perambulator 从磁盘重复读取

当前每个 `(t_snk, t_src)` 循环内都读取 perambulator。但事实上 72 个 perambulator（每个 t_src 一个文件）可以预先全部加载到 CPU 内存（72 × 43.9 MB × 4 dsrc ≈ 12.6 GB——可能过多），或至少缓存最近使用的几个 t_src。

**建议**: 使用 LRU 缓存（`@lru_cache(maxsize=4)`）缓存最近读取的 perambulator。

---

### 🔵 P4. 两个版本都缺少 eigvec 加载缓存

每配置的本征矢加载耗时 9-51 秒，占总时间的 1-5%。如果同一配置的 eigvec 在多次运行中被复用（例如只重跑 OPE 不重跑 2pt），可通过检查 VVV 缓存自动跳过 eigvec 加载。
